Day 8 Reflection

The most difficult concept in this course was understanding how to scale a system without introducing unnecessary complexity. At first, it was tempting to add components such as caches, load balancers, and read replicas simply because large systems use them. I overcame this by practising a structured design process: clarify requirements, estimate traffic, identify the likely bottleneck, and introduce a component only when it solves a specific problem. Designing TicketHub helped me understand why correctness can matter more than speed in some situations. For example, preventing two customers from buying the same seat requires database transactions and uniqueness constraints, not just a fast cache.

Based on the feedback from my capstone presentation, I would improve the architecture explanation in QuickNotes. I would include more realistic numerical estimates, show how requests travel between the front end, API, and persistence layer, and demonstrate an error case more clearly. I would also explain each architectural decision in terms of the problem it solves and the trade-off it introduces. This would make the presentation easier to follow and show that I understand the reasoning behind the design, rather than simply listing technologies.

Next, I plan to learn Node.js and Express and connect a real PostgreSQL database to QuickNotes. This will help me turn my API and data-model designs into working backend code. After that, I want to learn more about automated testing, deployment, and system design so I can build applications that are reliable, secure, and scalable.
